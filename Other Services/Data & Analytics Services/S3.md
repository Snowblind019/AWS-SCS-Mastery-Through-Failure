# Amazon S3 Retention, Lifecycle, and Storage Classes

S3 retention, lifecycle management, and storage class selection are usually presented as cost topics, but in a security context they are the mechanism for data governance: how long evidence survives, who can destroy it, and whether a deletion request can actually be satisfied. Object Lock provides write-once-read-many protection enforced by the service rather than by policy, so an object under a compliance-mode retention period cannot be deleted or overwritten by anyone, including the account root and AWS itself, until the period expires. Lifecycle rules automate transition and expiration, which is what makes a retention schedule operational rather than aspirational, and which is also the most common accidental-destruction path when a rule is scoped more broadly than intended. Storage classes determine durability guarantees and retrieval latency, both of which matter during an incident when the logs you need are in Deep Archive with a twelve-hour restore. The thing to hold onto is that Object Lock is the only S3 control that survives a compromised administrator, so anything that must be preserved against an insider or an attacker with account access belongs behind it.

## How it works

- **Object Lock prerequisites.** Versioning must be enabled, and Object Lock must be enabled at bucket creation for new buckets. It applies retention to object versions, not to object names, so a "delete" on a locked object creates a delete marker while the protected version remains.

- **Governance mode.** Objects cannot be deleted or have their retention shortened by ordinary principals, but a principal holding `s3:BypassGovernanceRetention` can override. This is the mode for internal policy enforcement where a break-glass path is acceptable.

- **Compliance mode.** No one can delete the object version or shorten the retention period until it expires. Not an administrator, not the account root, not AWS Support. The only way to remove the data before expiry is to close the AWS account. This is the mode regulators mean when they require WORM storage.

- **Retention periods and legal holds.** A retain-until date can be set per object or applied by a bucket default configuration. A legal hold is a separate, indefinite flag with no expiry, removable by a principal with `s3:PutObjectLegalHold`, used for litigation and investigation preservation independent of the retention schedule.

- **MFA Delete.** A versioning-level setting requiring an MFA token to permanently delete an object version or to change the versioning state. It can only be enabled by the bucket owner root user using the CLI or API, not the console, which is why it is rarely deployed despite being frequently recommended.

- **Lifecycle rules.** Scoped by prefix, object tag, object size, or the whole bucket. Actions include transitioning current versions between storage classes, transitioning noncurrent versions, expiring current versions (which creates a delete marker on a versioned bucket), permanently deleting noncurrent versions after a specified number of days or retaining a specified number of newer versions, aborting incomplete multipart uploads, and removing expired delete markers.

- **Transition constraints.** Objects must be at least 128 KB to transition to Intelligent-Tiering, and minimum storage durations apply per class: 30 days for Standard-IA and One Zone-IA, 90 days for Glacier Flexible Retrieval, 180 days for Deep Archive. Early deletion is billed as if the object remained for the minimum, so aggressive lifecycle rules on small objects can cost more than doing nothing.

- **Storage class characteristics.** Standard for frequent access. Intelligent-Tiering for unpredictable patterns, with automatic movement between tiers and no retrieval charges. Standard-IA for infrequent access with millisecond retrieval and a retrieval fee. One Zone-IA for reproducible data, stored in a single Availability Zone and therefore not durable against AZ loss. Glacier Instant Retrieval for archives needing millisecond access. Glacier Flexible Retrieval with restores from minutes to hours. Glacier Deep Archive with restores from twelve to forty-eight hours. Express One Zone for single-digit millisecond latency in one AZ.

- **Interaction between Object Lock and lifecycle.** A lifecycle expiration action cannot delete an object version still under retention or legal hold. The rule silently does not apply, which means a compliance retention period longer than the lifecycle expiration wins, and the storage cost continues.

- **Replication and retention.** S3 Replication can carry Object Lock retention settings to the destination bucket when both buckets have Object Lock enabled. Cross-Region replication into a separate account with its own Object Lock configuration is the standard pattern for a log archive that survives compromise of the source account.

- **Encryption interaction.** SSE-S3, SSE-KMS, and DSSE-KMS all apply independently of Object Lock. S3 Bucket Keys reduce KMS request cost for high-volume buckets. Client-side encryption puts the key entirely outside AWS, which means a lost key is unrecoverable data regardless of retention configuration.

- **Audit and verification.** CloudTrail management events cover bucket configuration changes including Object Lock and lifecycle rule modifications. CloudTrail data events, enabled separately and billed per event, cover object-level `GetObject`, `PutObject`, and `DeleteObject`. S3 Inventory produces a scheduled report including each object's storage class, encryption status, replication status, and Object Lock retention mode and date, which is the practical way to prove retention posture across millions of objects.

## Retention and immutability options compared

| Mechanism | Enforced by | Survives a compromised admin | Survives account root | Reversible | Typical use |
|---|---|---|---|---|---|
| S3 Object Lock, compliance mode | S3 service | Yes | Yes | No, only by closing the account | Regulatory WORM, forensic evidence |
| S3 Object Lock, governance mode | S3 service | Only from principals lacking bypass | No | Yes, with `s3:BypassGovernanceRetention` | Internal policy with a break-glass path |
| S3 legal hold | S3 service | Only from principals lacking the permission | No | Yes, indefinite until removed | Litigation and investigation preservation |
| MFA Delete | S3 versioning | Yes, absent the MFA device | No, root holds the device | Yes | Additional friction on version deletion |
| Bucket policy deny on delete | IAM evaluation | No, an admin can edit the policy | No | Yes | Baseline hygiene, not immutability |
| SCP deny on delete | Organizations | Yes, for member accounts | Yes for members, no for management account | Yes, by the management account | Organization-wide guardrail |
| AWS Backup Vault Lock, compliance mode | AWS Backup | Yes | Yes | No after the cooling-off period | Immutable backups across services |
| Glacier Vault Lock | S3 Glacier vaults | Yes | Yes | No once locked | Legacy vault-based archives |

## What gets tested

- **Compliance mode versus governance mode** is the most reliably tested distinction. If the requirement says no one, including administrators or the root user, may delete the data before the retention period expires, the answer is compliance mode. If the requirement allows a documented override, governance mode.

- **Object Lock requires versioning and must be enabled at bucket creation.** A question asking how to add WORM protection to an existing bucket without Object Lock is answered by creating a new bucket and replicating or copying into it, not by enabling it in place. Note that AWS does support enabling Object Lock on some existing versioned buckets through a support process, but the exam-safe answer remains the new bucket.

- **Legal hold has no expiry and is independent of the retention period.** It is the answer for preserving data for an investigation of indeterminate length.

- **A log archive that survives account compromise** replicates to a separate account with Object Lock in compliance mode, an SCP denying deletion, and a restricted bucket policy. Same-account Object Lock alone is a weaker answer when the threat model includes a compromised administrator with access to lifecycle configuration.

- **Lifecycle expiration on a versioned bucket creates a delete marker.** Permanently removing data requires a noncurrent version expiration action plus expired delete marker cleanup. Answers that stop at the expiration action leave the data and the cost in place.

- **Minimum storage durations and the 128 KB transition threshold** are the reason a lifecycle rule can increase cost. Expect a scenario with many small log objects where the correct answer is aggregating them or using Intelligent-Tiering rather than transitioning to Glacier.

- **Restore latency matters for incident response.** Deep Archive at twelve to forty-eight hours is the wrong destination for logs that may be needed during an active investigation. Glacier Instant Retrieval is the answer when archive economics and millisecond access are both required.

- **One Zone-IA is not multi-AZ durable.** Any question involving compliance data, audit logs, or anything not reproducible excludes it regardless of cost framing.

- **CloudTrail data events are separate, off by default, and billed per event.** Object-level access history requires enabling them, and the trail's destination bucket should itself be locked.

- **S3 Inventory is the evidence artifact** for proving encryption and retention state at scale, since checking millions of objects individually is not an answer.

## Limitations

- Compliance mode is genuinely irreversible. A mistakenly applied hundred-year retention on a large dataset means paying for that storage for a hundred years or closing the AWS account. There is no support escalation path.

- Object Lock protects object versions, not bucket existence in every sense: the bucket cannot be deleted while locked objects remain, which turns a misconfiguration into a permanent fixture of the account.

- MFA Delete can only be configured by the root user through the CLI or API, requires root credentials and a hardware or virtual MFA device, and interferes with automation. That operational cost is why it is recommended more often than deployed.

- Lifecycle rules act on their own schedule, typically within 24 to 48 hours of the trigger, so they are not a mechanism for prompt deletion in response to a data subject request.

- A lifecycle rule scoped by prefix silently matches more than intended when object key conventions change. There is no dry-run, and expiration on a non-versioned bucket is unrecoverable.

- Storage class transitions carry a per-object request charge. For buckets with hundreds of millions of small objects the transition cost can exceed the storage savings.

- Object Lock does not apply to buckets in all storage configurations, and Express One Zone directory buckets do not support it, versioning, or lifecycle transitions in the same way general purpose buckets do.

- Replicating locked objects requires Object Lock on both source and destination and does not retroactively apply to objects written before replication was configured.

- Retention does not prevent reading. Object Lock guarantees the data still exists; it does nothing to prevent an attacker with `s3:GetObject` from exfiltrating it, which is a separate control surface entirely.
